## DEC-005 — 실시간 공정의 CSV 기반 시연 범위

- 질문일: 2026-11-17
- 상태: 확정
- 관련 체크리스트: 3. 기능별 업무 규칙 — 실시간 공정
- 확인한 현재 상태: FE에는 설비명, 상태, 생산 품목, 작업 진행률 및 설비 필터가 시연용 데이터로 표현되어 있으나 실제 공정·서버와 연결되어 있지 않다.
- 제안 완료 조건:
  1. 등록된 설비별 현재 상태, 생산 품목, 작업 진행률과 마지막 갱신 시각을 조회할 수 있다.
  2. 전체 설비와 개별 설비를 선택해 현황을 조회할 수 있다.
  3. 상태는 최소 `정상`, `주의`, `고장`, `미가동`을 구분한다.
  4. 정해진 갱신 주기에 따라 최신 데이터가 화면에 반영된다.
  5. 데이터 누락, 연결 실패 및 오래된 데이터를 정상 상태와 구분해 표시한다.
  6. 설비 상세에서 현재 작업과 최근 상태 변경을 확인할 수 있다.
- 제안 데모 시나리오: 전체 설비 현황 조회 → 특정 설비 선택 → 상태와 작업 진행률 확인 → 주의 상태 또는 오래된 데이터 확인 → 갱신 후 변경된 상태 확인
- 별도 결정 필요: 실제 데이터 원천, 수집·갱신 주기, 지연 허용 범위 및 실시간 제공 방식
- 요청자 추가 정보:
  - 최신 데이터 반영 기능은 구현할 수 있으나 MVP 시점에는 실제 최신 데이터가 유입되지 않을 가능성이 높다.
  - 과거 데이터는 CSV 파일로 제공할 예정이다. 최초 답변의 `svc`는 오타로 확인되었다.
- 검토 결과:
  - `최신 데이터 반영 기능`과 `실제 설비 데이터 연동`을 서로 다른 완료 조건으로 관리한다.
  - 실제 연동 전에는 과거 데이터를 이용한 시연 모드로 갱신 흐름을 검증하고, 화면과 문서에 시연 데이터임을 명시한다.
  - 실제 데이터 원천이 연결되지 않은 상태를 실시간 연동 완료로 기록하지 않는다.
- 수정 제안 완료 조건:
  1. 제공받은 과거 데이터를 서버에 적재하고 설비별 상태를 조회할 수 있다.
  2. 서버가 시연용 데이터의 기준 시각 또는 순서에 따라 다음 상태를 제공하고, FE가 정해진 주기로 이를 다시 조회해 반영한다.
  3. 화면에 데이터 기준 시각, 마지막 조회 시각 및 `시연 데이터` 여부를 표시한다.
  4. 데이터가 갱신되지 않거나 조회에 실패하면 오래된 데이터 또는 연결 오류 상태를 표시한다.
  5. 실제 설비 데이터 수집·연동은 별도 미완료 항목으로 명시한다.
- 확인 결과: `svc`는 `CSV`의 오타이며 과거 데이터 제공 형식은 CSV 파일이다.
- 답변: CSV 기반 시연 모드의 수정 완료 조건에 동의한다.
- 확정 결과:
  1. CSV 과거 데이터를 서버에 적재한다.
  2. 과거 데이터를 기준 시각 또는 행 순서에 따라 시연용으로 갱신한다.
  3. FE가 서버를 주기적으로 조회하여 변경된 설비 상태를 반영한다.
  4. 데이터 기준 시각, 마지막 조회 시각 및 `시연 데이터` 여부를 표시한다.
  5. 갱신 중단이나 조회 실패 시 오래된 데이터 또는 연결 오류로 표시한다.
  6. 실제 설비 데이터 수집·연동은 1차 MVP의 미완료 범위로 명시한다.

- 근거: 2026-11-17 대화 답변
- 남은 쟁점: CSV 필수 데이터, 상태 종류, 시연 갱신 주기, 지연·오래된 데이터 판정 기준

- ‘기존 보고서 보기’와 ‘다시 생성’을 제공한다. 다시 생성하면 현재 데이터로 새 보고서를 등록하고 기존 보고서도 보존하는 안이다.
- 요청자는 2026-11-18에 이 흐름에 동의하고 안내에서 기존 보고서를 수정하는 방법도 제안했다.
- 종류·집계 기간·대상이 같은 보고서 중 사용자가 조회할 수 있는 활성 보고서가 있으면 생성 전에 ‘같은 조건의 보고서가 있습니다’라고 안내한다.
- ‘기존 보고서 보기’와 ‘다시 생성’을 제공한다. 보고서를 선택해 수정 권한이 있으면 ‘기존 보고서 수정’으로 편집 화면을 열 수 있다.
- 기존 보고서를 수정하면 같은 보고서에 저장하고 기존 수정 이력 규칙을 적용한다. 다시 생성하면 현재 데이터로 새 보고서를 등록하고 기존 보고서는 보존한다.

## DEC-075 — 부서·라인·설비 매핑과 DB 설계 (Q-075)

- Q-006에서 확인한 CSV에는 설비 코드와 이름이 있다. 부서·생산 라인 정보는 확인하지 못했다.
- MVP에서 부서·라인·설비 연결을 시연용 DB 초기 데이터로 준비할까? 부서나 라인을 선택하면 연결된 CSV 설비의 기록을 집계한다.
- 같은 설비가 여러 선택 대상에 포함되면 한 번만 집계하는 안이다. 실제 조직 매핑을 확보하면 시연용 매핑을 교체한다.
- 요청자는 시연용 매핑과 중복 집계 방지에 동의했으며, 이후 테이블 설계에 반영해 달라고 요청했다.
- DB 설계에서 부서·라인·설비 연결, CSV 설비 코드와 내부 설비의 매핑, 계정별 복수 담당을 명시한다. 초기 데이터로 시연용 매핑을 제공하고 실제 매핑이 확보되면 교체할 수 있도록 설계한다.

## DEC-076 — 공정 CSV 재적재와 중복 처리 (Q-076)

- 같은 CSV를 다시 적재해도 생산·공정 이력과 집계 건수가 늘어나지 않도록 하자는 안이다.
- 이미 적재된 기록과 같은 원본 식별자로 다른 내용이 들어오면 기존 기록을 보존하고 충돌을 알려 확인할 수 있게 할까?
- 사용할 원본 식별자와 유일성 범위는 기준 CSV를 정한 뒤 확인한다. CSV 헤더에 있는 `_id`만으로 파일 간 유일성을 가정하지 않는다.
- 요청자는 중복 방지와 충돌 처리에 동의했고, 운영에서는 CSV 적재를 자주 하는지와 설비 데이터가 DB로 들어오는 경로를 물었다.
- 같은 CSV를 다시 적재해도 이력과 집계 건수가 늘어나지 않는다. 같은 원본 식별자로 내용이 다른 기록이 들어오면 기존 기록을 보존하고 충돌을 알린다.
- 운영 연동 참고로, 설비 데이터는 PLC와 수집기 등을 거쳐 자동 전송할 수 있다. MVP에서는 과거 CSV를 초기·시연 데이터로 적재하며, 실제 설비 연동 방식은 추후 설비 환경에 맞춰 정한다.

### Q-077 — MVP 공정 데이터의 기준 CSV (프론트 화면 확인 후 재논의)

- 요청에 따라 기준 CSV 선정은 보류한다. 프론트 화면이 만들어지면 화면에 필요한 데이터를 확인한 뒤 파일을 선정하고 원본 식별자와 시간대를 검증한다.

## DEC-078 — AI 보고서 생성 권한과 화면 노출 (Q-078)

- 사용자는 관리자·고용자 모두에게 생성 권한을 부여한다고 명확히 했다. 관리자 프론트엔드에서 생성 기능을 제공할지는 미정이다.

## DEC-079 — AI 보고서 집계와 표·그래프 (Q-079)

- 생산·품질 지표는 백엔드에서 계산하고, 품질 리포트와 AI 보고서는 같은 집계 규칙을 사용하도록 할까?
- AI는 계산된 수치와 조회한 기록으로 본문을 작성한다. 예를 들어 불량률은 DEC-029의 계산식을 공통으로 적용하고, 근거가 없는 원인이나 수치는 본문에 넣지 않는 안이다.
- 요청자는 집계 기준에 동의하고, 보고서에 표와 그래프를 넣되 사용할 수 있다면 Seaborn이나 Matplotlib을 사용해 달라고 했다.
- 백엔드에서 공통 집계 규칙으로 수치를 계산하고, AI는 집계 결과와 확인된 기록으로 본문을 작성한다. 보고서의 표와 그래프도 같은 집계 결과를 사용하며 데이터가 없는 항목은 DEC-071을 따른다.
- 구현 기본안은 표를 Markdown으로 구성하고 Matplotlib으로 그래프를 렌더링해 보고서 화면과 PDF에 넣는 것이다. Seaborn은 필요한 차트가 있을 때 검토한다.

## DEC-080 — 생성 시점의 보고서 집계 결과 보존 (Q-080)

- 보고서를 생성할 때 집계에 사용한 기간·대상·수치를 함께 저장할까?
- 기존 보고서 화면과 PDF는 저장한 수치로 표·그래프를 만든다. 이후 원본 데이터가 바뀌어도 본문과 수치가 어긋나지 않으며, 사용자가 ‘다시 생성’을 선택하면 현재 데이터로 새 보고서를 등록하는 안이다.
- 요청자가 동의했다. 보고서 생성 시 집계 기간·대상·수치를 저장하고 기존 보고서 화면과 PDF에 당시 집계 결과를 사용한다. ‘다시 생성’은 현재 데이터를 사용해 새 보고서를 등록한다.

## DEC-081 — 기존 보고서의 편집 범위 (Q-081)

- 수정 권한이 있는 사용자는 제목과 본문을 편집할 수 있게 할까?
- 집계 기간·대상과 자동 표·그래프의 수치는 생성 당시 값으로 유지하고, 이 값을 바꾸려면 조건을 다시 선택해 새 보고서를 생성하는 안이다.
- 요청자는 이 방안에 동의했다. 수정 권한이 있는 사용자는 제목과 본문을 편집할 수 있다. 집계 기간·대상·수치는 생성 당시 값으로 유지하며, 집계 조건이나 수치를 바꾸려면 새 보고서를 생성한다.

## DEC-082 — 화면 이동과 AI 보고서 생성 (Q-082)

- 생성 요청이 접수되면 ‘생성 중’으로 안내하고, 사용자가 다른 화면으로 이동하거나 새로고침해도 서버에서 작업을 계속하도록 할까?
- 성공한 보고서는 ‘올라온 보고’에 등록한다. 실패 상태와 같은 조건으로 다시 시도하는 동작은 요청자에게 보여주는 안이다(DEC-072).
- 요청자는 생성 중 화면을 나가면 보통 작업 자체가 취소되는지 물었다.
- 검토 의견은 서버가 접수한 보고서 생성 작업을 화면과 별도로 처리하는 것이다. 화면 이동이나 새로고침 후에도 진행 상태와 결과를 다시 볼 수 있다. 명시적 취소가 필요하다면 별도의 동작으로 설계한다.
- 요청자는 이 방안에 동의했다. 서버가 접수한 생성 작업은 화면 이동이나 새로고침 후에도 계속한다. 요청자는 생성 상태와 결과를 다시 확인할 수 있다. 성공하면 ‘올라온 보고’에 등록하고, 실패하면 DEC-072에 따라 안내하고 재시도를 제공한다.

## DEC-083 — 보고서 생성 중 중복 요청 (Q-083)

- 같은 사용자가 동일한 종류·집계 기간·대상의 보고서를 생성하는 동안 다시 요청하면, 새 작업을 시작하지 않고 진행 중인 작업을 보여줄까?
- 연속 클릭이나 네트워크 재전송으로 동일한 요청이 다시 들어오면 같은 작업 또는 결과를 반환하는 안이다. 완료된 보고서에 대해 사용자가 명시적으로 ‘다시 생성’을 선택하면 DEC-074에 따라 새 작업을 시작한다.
- 요청자는 기존 보고서가 생성 중임을 확인한 뒤 새 데이터를 반영하려고 의도적으로 다시 생성하는 경우의 처리를 물었다.
- 수정 검토안은 같은 요청의 연속 클릭·재전송에는 기존 작업이나 결과를 반환하고, 사용자가 생성 중 안내에서 ‘최신 데이터로 새로 생성’을 명시적으로 선택하면 기존 작업을 계속하면서 새 작업을 접수하는 것이다.
- 각 작업은 접수 시점의 집계 기준 시각을 사용하고 보고서에 표시하는 안이다. 같은 종류·기간·대상이라도 명시적으로 새로 생성하면 별도 보고서로 등록한다. 기준 시각과 새 작업 정책은 확정 대기다.
- 요청자는 프론트에서 연속 클릭을 막을 수 있는지 물었다. 클릭 직후부터 서버의 접수 응답을 받을 때까지만 버튼을 잠그는 안을 제안한다. 접수 후에는 진행 상태와 ‘최신 데이터로 새로 생성’을 제공한다.
- 서버에서는 동일 요청 식별자로 재전송된 요청에 기존 작업이나 결과를 반환하는 안이다. 사용자가 명시적으로 새로 생성하면 새 요청 식별자를 사용한다.
- 요청자는 이 방안에 동의했다. FE는 버튼을 누른 뒤 서버의 접수 응답을 기다리는 동안 버튼을 비활성화한다. 서버는 같은 요청 ID가 재전송되면 기존 작업 또는 결과를 반환한다. 접수 후 사용자가 ‘최신 데이터로 새로 생성’을 선택하면 기존 작업과 별도로 새 요청 ID를 발급해 처리한다.
- 집계 기준 시각과 표시 위치는 DEC-084에서 확정했다. CSV 시연 기준일은 DEC-070을 따른다.

## DEC-084 — 보고서 생성 요청의 집계 기준 시각 (Q-084)

- 서버가 생성 요청을 접수할 때 집계 기준을 고정할까? CSV 시연에서는 접수 당시 재생 중인 데이터 시각을 사용한다.
- 집계에는 사용자가 지정한 기간과 해당 시점까지 조회 가능한 데이터를 적용한다. 생성 중 새로 들어온 데이터는 ‘최신 데이터로 새로 생성’을 선택했을 때 반영한다.
- 저장한 기준 시각은 보고서 상세 화면과 PDF에 표시하는 안이다.
- 요청자는 이 방안에 동의했다. 서버 접수 시 집계 기준을 고정하며, CSV 시연에서는 접수 당시 재생 중인 데이터 시각을 사용한다. 사용자가 지정한 기간에서 그 시점까지 조회 가능했던 데이터만 집계한다.
- 접수 후 들어온 데이터는 ‘최신 데이터로 새로 생성’한 보고서에 반영한다. 집계 기준 시각을 저장하고 보고서 상세 화면과 PDF에 표시한다.

## DEC-085 — 잘못 등록한 재고 변경의 정정 (Q-085)

- 관리자 사후 확인에서 잘못된 입출고·수량 조정을 발견하면 원래 기록을 보존하고, 사유와 원래 기록을 연결한 정정 내역을 추가하는 안이다.
- 예를 들어 실제로 8개를 출고했는데 10개로 등록했다면, 2개를 되돌리는 정정을 추가해 현재 수량에 즉시 반영한다.
- 관리자와 고용자 중 누가 정정을 등록할 수 있는지는 별도로 정한다.
- 요청자는 이 방안에 동의했다. 원래 변경 기록을 보존하고, 해당 기록에 연결된 정정 이력에 사유와 정정 수량을 남긴다. 정정 수량은 등록 즉시 현재고에 반영한다.

## DEC-086 — 재고 정정 등록 권한 (Q-086)

- 관리자는 모든 재고 변경을 정정하고, 고용자는 본인이 등록한 재고 변경만 정정할 수 있도록 할까?
- 고용자의 정정도 수량에 즉시 반영하고 관리자가 사후 확인한다. 정정 사유·등록자·원래 기록을 이력으로 남기는 안이다.
- 요청자는 이 방안에 동의했다. 관리자는 모든 재고 변경을, 고용자는 본인이 등록한 변경만 정정할 수 있다. 고용자의 정정은 즉시 수량에 반영하고 관리자가 사후 확인한다. 정정 사유·등록자·원래 기록을 이력으로 남긴다.

## DEC-087 — 재고 단위와 음수 수량 (Q-087)

- 완제품 수량은 정수 ‘개’ 단위로 관리하고, 출고·조정·정정으로 현재고가 0 미만이 되는 요청은 차단할까?
- 실제 수량과 시스템 수량이 다르면 사유를 남긴 재고 조정으로 맞추는 안이다.
- “ㅡ래”라는 답변은 직전 제안에 동의한 것으로 해석했다. 완제품 수량은 정수 ‘개’ 단위로 관리한다. 출고·조정·정정으로 현재고가 0 미만이 되는 요청은 차단한다. 실제 수량과 시스템 수량이 다르면 사유를 남긴 조정으로 맞춘다.

## DEC-088 — 관리자 확인 후 재고 기록 정정 (Q-088)

- 고용자는 관리자 확인 전까지 본인이 등록한 기록을 정정할 수 있고, 관리자 확인이 끝난 기록의 정정은 관리자만 가능하도록 할까?
- 사후 확인 완료 여부와 확인자·확인 시각을 기록하는 안이다.
- 요청자는 보고서와 같은 권한 규칙을 적용하도록 했다. 고용자는 관리자 확인 전까지 본인이 등록한 기록을 정정할 수 있고, 확인 후에는 관리자만 정정할 수 있다. 확인 완료 여부·확인자·확인 시각을 기록한다.

## DEC-089 — 부족 재고 경고 (Q-089)

- 품목별로 최소 재고 수량을 지정하고 현재고가 그보다 적으면 목록에 ‘재고 부족’을 표시할까? 기준이 없는 품목에는 경고를 표시하지 않는 안이다.

## DEC-090 — 인수인계 노트의 MVP 범위 (Q-090)

- 현재 홈의 인수인계 노트를 MVP에서 DB에 저장하고 공유하도록 할까?

- 요청자는 진행에 동의했다. 인수인계 노트를 DB에 저장·공유한다. 관리자와 고용자 모두 작성·조회할 수 있으며, 본인 노트 수정과 읽은 사용자의 확인 표시를 제공한다.

## DEC-091 — 인수인계 확인 기록 (Q-091)

- 확인 표시는 사용자별로 확인자·확인 시각을 기록하고, 노트 본문이 수정되면 기존 확인은 이전 내용에 대한 기록으로 보존하며 수정된 내용의 재확인을 받도록 할까?
- 요청자는 인수인계를 작성한 뒤 이전 사용자가 다시 확인·수정할 일이 있는지 물었다.
- 검토안은 작성 후 다음 근무자가 읽고 확인하는 기본 흐름을 중심으로 한다. 본인 노트 수정은 기존 결정대로 제공하고, 수정되면 수정 시각을 표시한다. 수정에 따른 일괄 재확인 요청은 MVP에서 생략하며, 중요한 추가 내용은 새 노트로 남기는 안이다.
- 요청자는 간소화한 방안에 동의했다. 확인자·확인 시각을 기록하고 본문 수정 시 수정 시각을 표시한다. 수정 후 재확인은 필수로 요구하지 않으며 중요한 추가 내용은 새 노트로 남긴다.

## DEC-092 — 인수인계 담당 기본값과 조회 범위 (Q-092)

- 다른 담당 범위의 노트 조회 허용 여부는 별도로 정한다.
- 요청자는 동일한 로직으로 진행하도록 했다. 작성자의 담당 범위를 기본 대상으로 지정하고 조정할 수 있게 한다. 사용자는 본인 담당 관련 노트를 기본으로 보고, 관리자는 전체 노트를 조회한다. 다른 담당 범위 조회의 허용 여부는 아직 미정이다.

## DEC-093 — 삭제 데이터 복구 기능의 MVP 범위 (Q-093)

- 요청자는 복구 기능의 필요성을 질문한 뒤, soft delete로 보존하고 복구는 추후로 두도록 결정했다.
- MVP에서는 삭제 데이터를 soft delete로 보존하고, 휴지통·복구 기능은 추후 범위로 보류한다.

## DEC-094 — 서버 중단 후 보고서 생성 작업 처리 (Q-094)

- 요청자는 이 방안에 동의했다. 서버 중단으로 끝나지 못한 생성 작업은 중단 상태를 안내하고 조건을 유지해 사용자가 재시도할 수 있게 한다. 서버 복구 후 자동 재실행은 추후 범위로 보류한다.

## DEC-095 — AI 작업 상태 표시 (Q-095)

## DEC-096 — 보고서 생성 작업과 등록 보고서 표시 (Q-096)

- 요청자는 이 방안에 동의했다. ‘올라온 보고’에는 성공적으로 생성·등록된 보고서를 표시한다. 생성 중·실패·중단 작업은 요청자의 ‘내 생성 작업’ 영역에서 확인한다. 생성 단계와 보고서 업무 상태를 구분해 표시한다.

## DEC-097 — AI 대화 답변의 조회 근거 표시 (Q-097)

- AI 답변에 조회 기간·대상·집계 기준 시각을 함께 표시하고, 특정 보고서나 이력을 근거로 답했다면 권한이 있는 상세 화면으로 이동할 수 있게 할까?
- 시연 데이터를 사용한 답변에는 시연 여부를 표시하는 안이다.
- 요청자는 동의했다. 답변에 조회 기간·대상·집계 기준 시각과 시연 여부를 표시한다. 근거로 사용한 보고서·이력은 조회 권한이 있는 상세 화면으로 연결한다.

## DEC-098 — 과거 AI 답변과 최신 데이터 재조회 (Q-098)

- 대화 이력은 당시 답변과 조회 기준을 그대로 보관하고, 사용자가 ‘최신 데이터로 다시 조회’를 누르면 새로운 답변을 같은 대화에 추가하도록 할까?
- 시간이 지나 원본 기록이 삭제되거나 권한이 바뀌면, 상세 링크 접근 시 현재 권한과 삭제 상태를 다시 확인하는 안이다.
- 요청자는 동의했다. 과거 답변과 조회 기준을 보존하고, ‘최신 데이터로 다시 조회’하면 같은 대화에 새 답변을 추가한다. 근거 링크 접근 시 현재 권한과 삭제 상태를 검증한다.

## DEC-099 — 권한 변경 후 과거 AI 답변 표시 (Q-099)

- 관리자가 고용자로 변경되는 등 근거 데이터의 조회 권한을 잃으면, 해당 데이터를 포함한 과거 AI 답변도 가려서 표시할까?
- 예를 들어 관리자 시절 조회한 타인 보고 내용은 현재 권한이 없으면 ‘현재 권한으로 볼 수 없는 답변입니다’로 표시하는 안이다. 원본 기록의 soft delete 이후 과거 답변 처리 기준은 별도 논의한다.
- 요청자는 이 방안이 맞다고 동의했다. 근거 데이터의 현재 조회 권한이 없으면 해당 데이터를 포함한 과거 AI 답변을 가리고 ‘현재 권한으로 볼 수 없는 답변입니다’로 표시한다.

## DEC-100 — 근거 기록 삭제 후 과거 AI 답변 표시 (Q-100)

- 근거 보고서나 이력이 soft delete되면 해당 내용이 담긴 과거 답변도 가리고 ‘근거 기록이 삭제된 답변입니다’라고 표시할까?
- 가려진 답변의 내용은 대화 검색 결과·미리보기와 이후 AI 대화 맥락에서도 제외하는 안이다. 권한으로 가린 답변에도 이 기준을 적용한다.
- 요청자는 근거가 사라진 과거 답변도 나중에 참고할 수 있으므로 다시 필터를 적용해 안내하는 편이 낫겠다고 제안했다.
- 수정 검토안은 과거 답변과 당시 조회 기준을 보존하고, 열람 시 현재 권한을 재검증하는 것이다. 삭제된 근거를 사용했던 답변은 ‘작성 당시 자료이며 근거가 삭제됨’을 표시해 과거 참고용으로 제공한다. 현재 권한이 없는 내용은 DEC-099에 따라 가린다.
- 최신 재조회는 현재 권한과 soft delete 필터를 적용해 새 답변을 추가한다. 과거 답변의 삭제된 근거 내용을 이후 AI에 전달할지는 별도 결정한다.
- 요청자는 수정안에 동의했다. 과거 답변 열람 시 현재 권한을 확인하고, 허용된 답변은 ‘작성 당시 자료이며 근거가 삭제됨’을 표시해 참고용으로 제공한다. 권한이 없는 내용은 가린다. 최신 재조회에는 현재 권한과 삭제 필터를 적용한다.

## DEC-101 — 이후 AI 대화에 전달할 과거 답변 (Q-101)

- 사용자가 삭제된 근거를 담은 과거 답변에 이어 질문하면, 현재 권한이 있는 과거 답변을 작성 시각·근거 삭제 상태와 함께 AI에 전달할까?
- AI는 이를 과거 참고 자료로 취급하고 현재 사실에 대한 질문은 현재 데이터로 다시 조회하는 안이다. 현재 권한이 없는 내용은 전달하지 않는다.
- 요청자는 동의했다. 현재 권한이 있는 과거 답변을 작성 시각·근거 삭제 상태와 함께 AI에 전달해 과거 참고 자료로 사용한다. 현재 상황에 대한 질문은 현재 데이터로 다시 조회하며, 권한이 없는 내용은 전달하지 않는다.

## DEC-102 — AI 작업 진단 기록 (Q-102)

- AI 조회·보고서 생성에 대해 요청자, 작업 종류, 시작·종료 시각, 성공·실패·중단 결과와 오류 코드를 남길까?
- 일반 운영 로그에는 비밀번호·토큰·원본 개인정보와 대화 본문을 넣지 않고, 대화 내용은 기존 대화 저장소에서 권한에 따라 관리하는 안이다.
- 요청자는 로그 기록의 중요성에 동의했으며 나중에 추가로 논의할 내용이 있다고 했다.
- AI 작업의 요청자 식별자·작업 종류·시작/종료 시각·처리 결과·오류 코드를 기록한다. 일반 로그에는 비밀번호·토큰·원본 개인정보·대화 본문을 기록하지 않는다. 로그 관련 추가 요구사항은 후속 설명을 받은 뒤 반영한다.

## DEC-103 — 공통 API 오류 형식 (Q-103, FE 검토 대기)

- API 오류는 HTTP 상태 코드와 함께 `code`, `message`, `request_id`를 공통으로 반환하는 안으로 FE와 협의할까?
- 입력 오류에는 필드별 오류 정보를 추가하고 `request_id`로 서버 로그를 찾을 수 있게 한다. 사용자 응답에는 내부 SQL·스택·비밀값을 포함하지 않는다.
- 요청자는 공통 형식에 동의하면서 현재 기획에서 입력 오류가 발생할 필드가 많지 않아 보인다고 했다.
- FE 협의안은 HTTP 상태 코드와 `code`, `message`, `request_id`를 반환하는 것이다. 필드별 오류 정보는 입력 검증에 실패한 경우에만 선택적으로 포함한다. 사번·비밀번호 형식, 기간의 시작·종료 순서, 재고 수량과 필수값은 서버에서 검증한다.

## DEC-104 — 공통 API 성공 응답 (Q-104, FE 검토 대기)

- 성공 시 단건은 해당 데이터 객체를 반환하고 목록은 `items`와 페이지 정보를 반환하는 안으로 FE와 협의할까? 보고서 생성 접수는 작업 ID와 처리 상태를 반환하는 안이다.
- 요청자는 동의했다. FE 협의안은 단건 데이터 객체, 목록의 `items`와 페이지 정보, 보고서 생성 접수의 작업 ID와 처리 상태다. 구체적인 필드와 FE 승인은 API 계약 단계에서 정한다.

## DEC-105 — 쿠키 기반 토큰 보관·전송 (Q-105)

- 액세스·리프레시 토큰을 브라우저 어디에 보관하고 어떻게 서버로 보낼지 FE와 정한 기준이 있는지 확인한다. 아직 없다면 웹앱 구성과 배포 출처를 고려해 구현안을 검토한다.
- 요청자는 토큰을 쿠키에 담도록 했다. 액세스·리프레시 토큰을 쿠키로 보관·전송한다. 쿠키 속성과 요청 위조 방지 방식은 별도 설계한다.

## DEC-106 — 인증 쿠키 보안 기본안 (Q-106)

- 인증 쿠키에 HttpOnly를 적용하고 HTTPS 환경에서 Secure를 적용하며, 쿠키 자동 전송에 따른 CSRF 방어를 서버에 적용하는 기본안으로 할까?
- SameSite·Domain·Path·CORS의 구체적인 설정은 FE·BE 배포 출처가 정해지면 맞춘다.
- 요청자는 적용에 동의했고 관련 내용을 나중에 추가 설명해 달라고 했다. 인증 쿠키는 HttpOnly를 적용하고 HTTPS 환경에서는 Secure를 적용한다. 서버에 CSRF 방어를 적용하며 구체적인 방식은 설계 단계에서 정한다.
- 후속 설명 항목은 HttpOnly·Secure·SameSite·CSRF의 역할과 브라우저·서버 요청 흐름이다. 설명 시점은 후속 대화에서 정한다.

## DEC-107 — 폐기된 리프레시 토큰 재사용 (Q-107)

- 이미 교체·폐기된 리프레시 토큰이 다시 제출되면 갱신을 거부하고, 그 로그인 세션의 현재 리프레시도 폐기해 재로그인을 요구하도록 할까?
- 다른 기기에서 로그인한 별도 세션은 유지하는 안이다. 실제 동시 갱신 요청을 중복 전송과 구별하는 기준은 구현 설계에서 정한다.
- 요청자는 동의했다. 폐기된 리프레시가 다시 제출되면 갱신을 거부하고 해당 로그인 세션의 현재 리프레시도 폐기해 재로그인을 요구한다. 다른 기기의 별도 세션은 유지한다. 이미 발급된 액세스 토큰은 DEC-054의 만료 정책을 따른다.

## DEC-108 — 인수인계 노트 삭제 권한 (Q-108)

- 인수인계 노트는 관리자가 전체 노트를 삭제할 수 있고, 고용자는 본인 노트만 삭제할 수 있도록 할까? 삭제에는 공통 soft delete 정책을 적용한다.
- 요청자는 동의했다. 관리자는 전체 노트, 고용자는 본인 노트만 soft delete할 수 있다.

## DEC-109 — 다른 담당 범위의 인수인계 조회 (Q-109)

- 인수인계 노트는 고용자도 전체를 조회할 수 있게 하고, 기본 목록만 본인 담당으로 필터링할까? 본인이 담당하지 않는 부서·라인·설비의 노트도 필터를 바꿔 볼 수 있는 안이다.
- 요청자는 동의했다. 관리자와 고용자 모두 전체 노트를 조회할 수 있다. 고용자의 기본 목록은 본인 담당으로 필터링하고, 필터를 바꿔 다른 담당과 전체 노트를 조회할 수 있다.

## DEC-110 — 완료된 보고서의 관리자 수정 후 상태 (Q-110)

- 관리자가 완료된 보고서의 제목·본문을 수정하면 완료 상태를 유지하고 수정 이력만 남길까? 재처리가 필요하면 관리자가 기존의 ‘진행 중으로 되돌리기’를 사용하는 안이다.
- 요청자는 동의했다. 관리자 수정 후에도 완료 상태를 유지하고 수정 이력을 남긴다. 재처리가 필요하면 관리자가 직접 진행 중으로 되돌린다.

## DEC-111 — 로그인 실패 제한 (Q-111)

- 같은 계정의 비밀번호가 5회 연속 틀리면 5분 동안 로그인 시도를 제한하는 초기값으로 시작할까? 성공하면 연속 실패 횟수를 초기화하고 횟수·제한 시간은 설정값으로 관리하는 안이다.
- 요청자는 동의했다. 동일 계정에서 비밀번호를 5회 연속 틀리면 5분간 로그인 시도를 제한한다. 로그인 성공 시 실패 횟수를 초기화하고 횟수·시간은 설정값으로 관리한다.

## DEC-112 — 로그인 유지 선택 제외와 근무 종료 로그아웃 (Q-112)

- 요청자는 로그인 유지 기능도 추가할지 물었다.
- 기존 DEC-052는 로그인 시점부터 7일 유지다. 로그인 화면에 ‘로그인 유지’를 제공하면 선택 시 기존 7일, 미선택 시 8시간으로 구분하는 안을 검토한다. 액세스 15분과 리프레시 교체 정책은 동일하게 적용한다.
- 요청자는 로그인 유지 선택 기능을 제외하도록 했다. 근무 종료 전에 야근 버튼을 누르지 않으면 자동 로그아웃하는 기능이 있다고 설명했다.
- 로그인 유지 체크박스와 선택 여부에 따른 7일·8시간 구분은 도입하지 않는다. 근무 종료 전 야근 버튼을 누르지 않으면 자동 로그아웃한다.
- 근무 종료·연장 시간과 기존 토큰 7일 기한의 관계, 자동 로그아웃의 서버 처리 기준은 추가 확인한다.

## DEC-113 — 사용자별 근무 종료와 야근 연장 (Q-113)

- 근무 종료 시각과 야근 버튼을 눌렀을 때의 연장 시간은 이미 정해져 있는지 확인한다. 사용자별 근무시간인지 공통 근무시간인지도 확인한다.
- 요청자는 사용자별 근무시간이라고 답했다. 근무 종료·자동 로그아웃 기준은 사용자별 근무시간을 사용한다.
- 야근 연장 방식과 시간은 아직 미정이다.
- 다음 질문은 야근 버튼을 누를 때 연장 종료 시각을 직접 지정할지, 정해진 시간만큼 연장할지다.
- 요청자는 기본 1시간 연장, 종료 시각 직접 지정 가능, 항상 로그아웃 10분 전 알림을 요구했다.
- 사용자별 근무 종료 시각을 기준으로 야근 버튼의 기본 연장은 1시간이다. 사용자가 연장 종료 시각을 직접 지정할 수도 있다. 근무 종료와 연장 종료를 포함해 자동 로그아웃 10분 전에 알린다.

## DEC-114 — 근무 종료 후 재로그인 허용 (Q-114)

- 사용자별 근무·연장 종료 시각이 지나면 서버에서도 업무 API 요청과 토큰 갱신을 거부하고 해당 세션을 로그아웃 처리할까?
- 이후 재로그인은 다음 근무가 시작되면 허용할지, 근무 종료 후에도 새 로그인은 허용할지 확인이 필요하다.
- 요청자는 연장을 실수로 놓칠 수 있으므로 근무 종료 후에도 다시 로그인할 수 있어야 한다고 했다.
- 근무 종료로 자동 로그아웃된 이후에도 사번·비밀번호로 재로그인할 수 있다. 다음 근무 시작까지 접속을 제한하는 정책은 적용하지 않는다.
- 최초 질문의 서버 측 세션 처리 방식은 이번 답변으로 확정되지 않았다.

## DEC-115 — 근무 종료 후 재로그인의 이용 종료 시각 (Q-115)

- 근무 종료 후 재로그인하면 야근 종료 시각을 확인하도록 하고, 기본값은 재로그인 시점부터 1시간으로 제시할까? 사용자가 직접 시각을 바꿀 수 있고 종료 10분 전 알림을 적용하는 안이다.
- 요청자는 동의했다. 재로그인 시 새 야근 종료 시각을 확인한다. 기본값은 재로그인부터 1시간이며 사용자가 변경할 수 있다. 종료 10분 전 알림을 적용한다.

## DEC-116 — 사용자별 기본 근무시간 제공 방식 (Q-116)

- MVP에서는 사용자별 기본 근무 시작·종료 시각을 계정과 함께 DB 초기 데이터로 준비할까? 근무표 등록·편집 화면과 외부 근태 시스템 연동은 추후 범위로 두는 안이다.
- 요청자는 동의했다. 사용자별 기본 근무 시작·종료 시각은 계정과 함께 DB 초기 데이터로 준비한다. 근무표 등록·편집 화면과 외부 근태 시스템 연동은 추후 범위로 보류한다.

## DEC-117 — 화면 복귀 시 근무 종료 확인 (Q-117)

- 탭을 닫거나 PC가 절전 상태였다가 돌아왔을 때 이미 이용 종료 시각이 지났으면, 연장 안내를 새로 시작하지 않고 로그아웃 후 재로그인하도록 할까?
- 서버 시각으로 종료 여부를 확인하고, 10분 전 알림 구간에 복귀했다면 남은 시간을 즉시 안내하는 안이다.
- 요청자는 동의했다. 화면 복귀 시 서버 시각으로 종료 여부를 확인한다. 이미 종료됐다면 로그아웃 후 재로그인하며, 종료 10분 전 구간이라면 남은 시간을 즉시 안내한다.

## DEC-118 — 로그아웃 중 진행 중인 보고서 생성 (Q-118)

- 수동·자동 로그아웃 후에도 이미 접수된 보고서 생성은 계속하고, 재로그인하면 상태와 결과를 확인할 수 있도록 할까? 작업 실행에는 서버의 현재 권한을 적용하는 안이다.
- 요청자는 동의했다. 수동·자동 로그아웃 후에도 접수된 보고서 생성 작업을 계속하며 재로그인하면 상태와 결과를 확인할 수 있다. 작업 실행에는 서버의 현재 권한을 적용한다.

## DEC-119 — 근무 종료 자동 로그아웃의 토큰 처리 (Q-119)

- 근무 종료 자동 로그아웃도 일반 로그아웃과 같이 인증 쿠키를 제거하고 해당 세션의 리프레시 토큰을 폐기할까?
- 기존 액세스는 DEC-054대로 원래 만료까지 최대 15분 유효하다. 리프레시 7일은 상한이며, 실제 로그인은 근무 종료에 끝나고 재로그인으로 새 세션을 시작하는 안이다.
- 2026-11-19에 요청자는 동의했다. 근무 종료 자동 로그아웃도 쿠키를 제거하고 해당 세션의 리프레시를 폐기한다. 리프레시 7일은 상한이며 근무 종료 시 해당 로그인은 종료한다. 기존 액세스는 원래 만료까지 최대 15분 유효하고, 재로그인은 새 세션으로 처리한다.

## DEC-120 — AI 모델 최소 기준 (Q-120)

- 2026-11-19에 Q-044의 팀 연락 대기 항목을 재확인한다. AI 제공자·모델과 API 사용 예산에 대해 새로 정해진 내용이 있는지 묻는다.
- 요청자는 최소 스펙을 `gpt 5.6 sol`로 전달했다. 더 좋은 모델을 사용할 수도 있으나 확정된 것은 최소 기준뿐이다.
- 팀이 전달한 최소 기준 명칭을 그대로 기록한다. 상위 모델 채택은 미정이다. 실제 호출용 모델 ID·API 제공 경로·사용 가능 여부·예산은 확인 대기이며 다른 모델 이름으로 임의 치환하지 않는다.

## DEC-121 — 서버 관리용 로깅 기준 (Q-121)

- DEC-102에서 요청자가 나중에 추가로 논의할 로그 관련 내용이 있다고 했다. 현재 추가할 내용이 있는지 확인한다.
- 요청자는 서버 로그임을 확인하고, 앞으로 직접 개발할 때도 서버 관리 차원의 로그를 남겨야 한다고 했다.
- AI 작업을 포함한 서버 요청·오류·인증·상태 변경을 추적할 수 있게 로깅을 개발 기준으로 적용한다.
- 구현 기본안은 공통 로거를 통해 요청 ID, 메서드·경로, 응답 상태와 처리 시간을 남기고, 예외는 서버에서 원인 추적이 가능하도록 기록하는 것이다. 로그인 실패·로그아웃·서버 시작과 종료도 기록한다. 비밀번호·토큰·쿠키·대화 본문·원본 개인정보는 일반 로그에서 제외한다.
- 로깅 설정과 사용 예시는 백엔드 초기 구성 때 반영한다. 로그 저장 위치·보존 기간·수집 도구는 배포 환경 결정 후 정한다.

## DEC-122 — 목록 페이지 이동과 표시 기준 (Q-122, FE 검토 대기)

- 기본 20건·최대 100건은 DEC-056을 따른다. MVP 목록은 페이지 번호로 이동하는 방식으로 시작할까? API에는 페이지 번호·페이지 크기를 전달하고, 서버는 offset 방식으로 조회하는 안이다. AI의 다음 결과 조회에도 같은 조회 조건·정렬을 유지한다.
- 요청자는 동의하며 기본 표시를 10개로 변경하고 사용자 표시 개수 선택·검색·필터·긴 페이지 번호의 가운데 ‘…’ 축약을 요구했다.
- 기본 10개·최대 100개로 페이지 번호 기반 offset 조회를 제공한다. 검색·필터는 서버에서 전체 조회 권한 범위에 적용한다. 세부 필터는 화면별 업무 데이터를 따른다. DEC-056의 기본 20개는 이 결정으로 변경한다.
- 구현 기본안은 첫·끝과 현재 페이지 주변 번호를 표시하고 생략 구간은 ‘…’으로 표시하는 것이다. 검색·필터·페이지 크기를 바꾸면 첫 페이지로 이동한다. FE 검토와 API 세부 필드는 남아 있다.

## DEC-123 — AI 대화 답변 표시 방식 (Q-123)

- 답변이 생성되는 내용을 조금씩 보여주는 스트리밍 방식과 완성 후 한 번에 표시하는 방식 중 어떤 것을 사용할지 확인한다.
- 요청자는 정보 조회가 많으므로 완성 후 표시가 적절해 보이지만, 단순 답변에는 스트리밍이 나을 수도 있다고 검토했다.
- 제안은 MVP에서 완성 후 표시로 통일하고 대기 중에는 DEC-095의 실제 단계 상태를 보여주는 것이다. 조회 결과·표·근거를 함께 표시하며 단순 답변 스트리밍은 사용성 확인 후 검토한다. 최종 확정은 대기한다.
- 요청자는 진행에 동의했다. MVP의 AI 대화 답변은 완성 후 한 번에 표시한다. 대기 중에는 실제 조회·답변 작성 단계를 표시한다. 단순 답변 스트리밍은 추후 검토한다.

## DEC-124 — AI 대화 실패 시 사용자 재시도 (Q-124)

- 조회·답변 생성에 실패하면 사용자 질문을 유지하고 해당 질문에 ‘다시 시도’를 제공할까?
- 실패 상태를 표시하고 재시도 결과는 같은 질문의 답변 영역에서 확인하는 안이다. SQL 문법·컬럼 오류의 내부 1회 재시도는 DEC-055를 따른다.
- 요청자는 동의했다. 조회·답변 생성 실패 시 질문을 유지하고 다시 시도 버튼을 제공한다. 재시도 결과는 같은 질문의 답변 영역에 표시한다.

## DEC-125 — 대화 요청 순서와 취소·재전송 (Q-125)

- 같은 대화에서 답변 생성 중에는 다음 질문을 작성할 수 있지만 전송은 완료·실패 후에 허용할까? 앞선 질문과 답변 순서를 유지하는 안이다.
- 요청자는 동의하고 생성 중인 답변을 취소한 뒤 다시 보낼 수 있으면 좋겠다고 했다.
- 한 대화에서는 답변 생성 중 다음 질문 작성은 허용하고 전송은 완료·실패·취소 후에 허용한다. 답변 생성 취소와 질문 수정 후 재전송을 제공한다.
- 구현 기본안은 취소된 요청을 식별하고 늦게 도착한 결과를 사용자 답변과 후속 대화 맥락에 추가하지 않는 것이다. 서버는 가능한 범위에서 진행 중인 조회·AI 호출에 취소를 전파한다. 취소 확인과 새 요청 순서를 서버에서 관리한다.

## DEC-126 — 화면 이동 중 AI 대화 생성 (Q-126)

- 대화 답변도 보고서처럼 화면 이동·새로고침 후 계속 생성하고, 돌아오면 답변이나 실패 상태를 확인할 수 있게 할까? 사용자가 취소 버튼을 누른 요청에는 DEC-125를 적용한다.
- 요청자는 진행에 동의했다. 화면 이동·새로고침 후에도 대화 답변 생성을 계속하며 돌아오면 답변이나 실패 상태를 확인할 수 있다. 직접 취소한 요청은 DEC-125를 따른다.

## DEC-127 — 진행 중인 보고서 생성 취소 (Q-127)

- ‘내 생성 작업’에서 진행 중인 보고서 생성을 취소할 수 있게 할까? 취소가 확정된 작업은 ‘취소됨’으로 표시하고 보고서를 등록하지 않는 안이다.
- 이미 완료·등록된 작업에는 취소 대신 기존 보고서 조회·수정·삭제 권한을 적용한다. 완료와 취소가 동시에 도착하는 상황은 서버에서 일관되게 처리한다.
- 요청자는 진행에 동의했다. ‘내 생성 작업’에서 진행 중 생성을 취소할 수 있다. 취소가 확정되면 ‘취소됨’으로 표시하고 보고서를 등록하지 않는다. 이미 등록된 보고서는 기존 조회·수정·삭제 권한을 따른다.

## DEC-128 — AI 보고서 작성용 데이터 전달 (Q-128)

- 실제 AI 호출에 사용자의 질문과 필요한 업무 조회 결과를 보낼 때, 팀에서 정한 데이터 전송·마스킹 기준이 있는지 확인한다.
- 인증 비밀값 제외는 DEC-061, 현재 권한 적용은 기존 결정에 따른다. 추가로 사번·이름·보고서 내용 등 업무 데이터의 전송 허용 범위는 확인이 필요하다.
- 요청자는 DB 조회 결과를 AI API에 전달해 보고서를 쓰는 흐름을 생각했으며, 모든 내용을 전달해야 하는지 물었다.
- 설명안은 서버에서 선택된 기간·대상과 권한에 따라 조회·집계한 결과를 AI에 전달하는 것이다. 기간·대상·기준 시각, 요약 수치, 이슈 작성에 필요한 기록, 데이터 누락·시연 여부를 포함한다.
- 개별 원본 행 전체보다 보고서 작성에 필요한 집계·근거를 우선 사용한다. 제목의 작성자 정보와 표·그래프는 서버가 저장된 결과로 구성할 수 있다. 필요한 상세 분석에는 해당 기록을 추가 제공한다. 실제 전송 항목과 팀 허용 범위는 미확정이다.
- 요청자는 이 구조에 동의했다. 서버가 권한과 기간·대상에 맞게 집계한 수치와 필요한 근거 기록, 기준 시각·시연·누락 정보를 AI에 전달해 본문을 작성한다. 표·그래프는 같은 저장 집계 결과로 서버에서 만든다. 실제 전송 필드와 팀 승인 기준은 추가 확인한다.

## DEC-129 — 부서·라인·설비의 임시 설계 관계 (Q-129)

- 시연용 조직 구조는 한 부서에 여러 생산 라인, 한 라인에 여러 설비가 소속되는 형태로 시작할까? 한 설비의 현재 소속 라인은 하나로 두고 사용자 담당은 부서·라인·설비에 복수 지정하는 안이다.
- 요청자는 우선 적용하고 이후 데이터셋과 함께 확인해 조정하도록 했다. 부서→라인→설비의 관계와 설비의 단일 현재 소속 라인은 임시 설계 가정으로 사용한다. 실제 도메인의 확정 제약으로 취급하지 않으며 데이터셋 검토 후 설계·제약을 조정한다.

## DEC-130 — 사용자 담당 정보 초기 제공 (Q-130)

- MVP에서 사용자별 부서·라인·설비 담당 정보도 계정·근무시간과 함께 DB 초기 데이터로 준비할까? 담당을 배정·변경하는 관리 화면은 추후 범위로 두는 안이다.
- 요청자는 동의했다. 계정별 복수 담당은 계정·근무시간과 함께 DB 초기 데이터로 준비한다. 담당 배정·변경 관리 화면은 추후 범위로 보류한다.

## DEC-131 — 최소 재고 기준값 관리 (Q-131)

- 품목별 최소 재고 수량은 관리자만 설정·변경하고, 고용자는 기준값과 부족 여부를 조회하도록 할까?
- 요청자는 동의했다. 관리자는 기준값을 설정·변경하고 고용자는 기준값과 부족 여부를 조회한다.

## DEC-132 — 테스트 DB 구성 (Q-132)

- DB 연동 테스트는 개발 DB와 별도인 테스트용 PostgreSQL에서 실행하고, 테스트 시나리오별 초기 데이터로 검증하도록 할까?
- 로그인·역할별 권한, 재고 수량 변경, 보고서 등록과 중복 요청, AI 조회 권한을 실제 PostgreSQL 기준으로 검증하는 안이다.
- 요청자는 동의했다. DB 연동 테스트는 개발 DB와 별도의 PostgreSQL에서 테스트용 초기 데이터로 실행한다. 권한·수량 변경·보고서 등록과 중복 요청·AI 조회 권한을 검증한다.

## DEC-133 — dev 기반 브랜치와 MR (Q-133)

- 현재 저장소는 dev 브랜치를 사용하고 있으나 AGENTS.md에는 개발 브랜치가 팀 확인 필요로 남아 있다. 팀의 공통 개발 브랜치를 dev로 확정했는지 확인한다.
- 요청자는 dev가 맞으며 dev 기준으로 작업 브랜치를 만들고 dev로 MR을 보내도록 했다.
- FE·BE의 공통 개발 브랜치는 dev다. 작업 브랜치는 최신 dev에서 분기하고 MR 대상은 dev로 지정한다. 실제 브랜치 생성·커밋·push·MR 실행은 요청된 구현 작업의 범위와 Git 규칙에 따른다.

### Q-134 — 기존 Git 규칙 적용 (기존 문서 우선)

- 팀 작업 브랜치는 프로젝트명 없이 `be-feature-도메인`, `be-hotfix-도메인` 형태로 정할까? 기존 원격 FE 브랜치의 `fe-feature-home` 형태와 맞추는 안이다.
- 요청자는 AGENTS.md에 Git Convention이 이미 있다고 지적했다. 확인 결과 8절에 소문자 브랜치명·feature/hotfix·커밋 규칙, 9절에 MR 규칙이 있다. 브랜치 형식은 프로젝트명을 포함한 원문과 생략한 예시가 함께 있고 ‘팀 확인 필요’로 표시되어 있다.
- 기존 규칙을 우선 적용하며 이 질문의 제안은 새 규칙으로 확정하지 않는다. 개발 브랜치 dev와 MR 대상 dev는 DEC-133에서 확인됐다.
- 요청자는 기존 문서를 따르고 dev 기준으로 작업하는 정리에 동의했다. 브랜치명 원문·예시의 차이는 문서상 확인 사항으로 남긴다.

## DEC-135 — 핵심 데모 시나리오 (Q-135)

- 기본 데모를 ‘고용자 로그인 → 담당 공정·품질 확인 → 자연어 조회 → AI 보고서 생성 → 관리자 목록 조회·확인’ 순서로 구성할까?
- 재고 입출고·사후 확인, 일정 CRUD, 인수인계, 근무 종료 알림·야근 연장은 개별 시연으로 확인하는 안이다.
- 요청자는 동의했다. 고용자 로그인 → 담당 공정·품질 확인 → 자연어 조회 → AI 보고서 생성 → 관리자 목록 조회·확인을 핵심 데모로 사용한다. 재고·일정·인수인계·근무 종료 알림·야근 연장은 개별 시연으로 확인한다.

## DEC-136 — 시연 데이터의 공통 기준 (Q-136)

- 시연용 검사·재고 데이터는 최종 선정한 공정 CSV의 품목·설비·기간에 맞춰 준비할까? 같은 대상과 기간을 선택하면 공정·검사·품질·AI 보고서를 연결해 확인할 수 있도록 하는 안이다.
- 검사·재고 수치는 시연용임을 표시하고 CSV의 실제 관측값과 구분한다. 재고 수량은 생산 기록 건수와 일치한다고 가정하지 않는다.
- 요청자는 동의했다. 최종 CSV 선정 후 검사·재고 시연 데이터의 품목·설비·기간을 맞춰 연결된 데모를 준비한다. 시연 여부를 표시하며 재고 수량과 생산 기록 건수의 일치를 가정하지 않는다.

## DEC-137 — 보고서 버전과 동시 수정 충돌 (Q-137)

- 다른 사용자가 먼저 수정한 보고서를 저장하려 하면 ‘다른 사용자가 수정했습니다’를 안내하고 저장을 막을까?
- 작성 중인 내용은 유지하고 최신 내용을 다시 확인한 뒤 저장하게 해 다른 사람의 수정을 덮어쓰지 않도록 하는 안이다.
- 요청자는 보고서에 버전을 추가하는 방안을 고려했다고 했다.
- 검토안은 보고서별 정수 버전을 두고, 저장 시 사용자가 열었던 버전과 현재 버전을 원자적으로 비교하는 것이다. 일치하면 수정·이력 기록과 버전 증가를 같은 트랜잭션에서 처리한다. 불일치하면 현재 입력을 보존한 채 충돌을 안내한다.
- 기존 수정 이력에 버전 번호를 연결하고, 생성 당시 집계 결과의 고정 규칙은 DEC-080·DEC-081을 따른다. 상태 변경 등 편집 가능성에 영향을 주는 변경도 충돌 검사에 포함하는 구체적인 설계는 후속 단계에서 정한다.
- 요청자는 진행에 동의했다. 보고서 버전을 저장 시 비교하고 불일치하면 입력을 유지하며 충돌을 안내한다. 성공 시 수정·버전 증가·이력 기록을 같은 트랜잭션에서 처리한다. 생성 당시 집계 결과는 고정한다.

## DEC-138 — 보고서 수정 이력 권한과 확인 화면 (Q-138)

- 해당 보고서를 조회할 수 있는 사용자는 이전 버전의 내용·수정자·수정 시각도 조회할 수 있게 할까? 현재 보고서 조회 권한과 soft delete 규칙을 적용하는 안이다.
- 요청자는 권한에 동의했으며 이력을 어떻게 확인할지 질문했다.

- 요청자는 화면 방안에 동의했다. 상세 화면의 수정 이력 버튼에서 버전·수정자·시각 목록을 열고, 선택한 버전의 제목·본문을 읽기 전용으로 확인한다. 현재 보고서로 돌아가는 동작을 제공한다.

## DEC-142 — Python·PostgreSQL 개발 기준 버전 (Q-142)

- 제안은 Python 3.14와 PostgreSQL 18이다. 팀·CI·개발·테스트 환경을 같은 버전 계열로 맞추고, 초기 구성 때 설치·통합 테스트를 통과한 패치 버전과 의존성을 고정한다. 아직 실제 설치·통합 검증은 수행하지 않았다.
- 참고 자료는 https://devguide.python.org/versions/ , https://www.postgresql.org/support/versioning/ , https://pypi.org/project/fastapi/ , https://pypi.org/project/SQLAlchemy/ , https://pypi.org/project/matplotlib/ 이다.
- 요청자는 두 버전이 LTS인지 물었다. Python과 PostgreSQL은 별도 LTS 버전을 구분하는 정책 대신 버전별 지원 수명을 제공한다. Python 3.14의 지원 종료 예정은 2030년 10월이며 PostgreSQL 18은 2030년 11월 14일까지 지원한다. 버전 선택은 아직 제안 상태다.
- 요청자는 설명 후 동의했다. 개발 기준은 Python 3.14와 PostgreSQL 18로 확정한다. 팀원·CI·개발·테스트의 버전 계열을 맞추고 초기 설치·통합 검증 후 패치 버전을 고정한다.

## DEC-143 — DB 기본키와 업무 식별자 (Q-143)

- 계정·보고서·일정·재고 등 내부 기본키는 자동 증가 bigint로 시작할까? 사번·설비 코드 같은 업무 식별자는 별도 필드로 저장하고 필요한 유일성 제약을 적용하는 안이다.
- 요청자는 UUID가 과도한 선택인지 물었다. 검토 의견은 이번 규모에서도 UUID를 사용할 수 있으며, 숫자 ID보다 저장·인덱스 크기가 커지는 비용이 있지만 별도 분산 인프라가 필요한 것은 아니라는 것이다.
- PostgreSQL 18은 uuidv7()을 제공한다. UUID를 선택한다면 시간 순서 특성을 가진 UUIDv7을 기본안으로 검토한다. 실제 기본키 선택은 아직 미확정이다.
- 요청자는 회원가입 없이 직접 계정을 적재할 때 UUID가 불편할 수 있다고 질문했다.
- 설명안은 UUID 기본값을 DB에 두면 초기 계정 적재에서 ID를 생략할 수 있고, 사번으로 계정을 찾아 담당·근무시간을 연결할 수 있다는 것이다. bigint도 같은 초기 적재 방식이 가능하다.
- 검토 의견은 수동 조회와 초기 데이터 확인의 편의가 우선이라면 bigint를 선택하고, 초기 데이터 적재 스크립트에서 사번·설비 코드를 내부 ID로 연결하는 것이다. 회원가입 제공 여부가 UUID 선택을 제한하지는 않는다. 최종 선택은 미확정이다.
- 요청자는 bigint 방안에 동의했다. 계정·보고서·일정·재고 등 내부 기본키는 자동 증가 bigint를 기본으로 한다. 사번·설비 코드는 별도 고유 필드로 관리하고, 초기 데이터는 해당 업무 식별자로 내부 ID를 찾아 연결한다. 세부 유일성 범위는 데이터셋과 테이블 설계에서 검증한다.

## DEC-145 — 공통 생성·수정·삭제 시각 (Q-145)

- 업무 리소스에 created_at·updated_at을 두고, soft delete 대상에는 삭제 전 NULL인 deleted_at을 두는 기준으로 할까? 삭제 시 삭제 시각을 기록하고 일반 조회는 deleted_at이 NULL인 데이터를 대상으로 하는 안이다.
- 요청자는 진행에 동의했다. 업무 리소스에 created_at·updated_at을 두고 soft delete 대상에 deleted_at을 둔다. 삭제 전에는 NULL이며 삭제 시 시각을 기록한다. 일반 조회는 deleted_at이 NULL인 리소스를 대상으로 한다. 과거 AI 답변의 근거 삭제 표시는 DEC-100의 예외 정책을 따른다.

## DEC-146 — 사번 유지와 삭제 계정의 보고서 보존 (Q-146)

- 삭제된 계정까지 포함해 사번을 고유하게 유지한다. 계정은 soft delete하고 보고서·작성자 연결·수정 및 다운로드 이력은 보존한다. 관리자 보고서 조회는 작성자의 활성 여부와 관계없이 허용한다. 보고서 자체의 soft delete에는 기존 조회 제외 정책을 적용한다.

## DEC-152 — FE·BE 공통 API 기본안 공동 확인 (Q-152)

- 요청자는 1~10, 11~20처럼 하단 번호를 10개씩 묶는 의미라고 확인했다. 페이지당 기본 항목 10개·사용자 표시 개수 선택·최대 100개는 유지한다. DEC-122의 가운데 축약 기본안은 번호 묶음 이동 방식으로 변경한다. 나머지 공통 API 기본안의 FE·BE 공동 확인은 대기 중이다.
- 요청자는 나머지 기본안도 진행하도록 동의했다. FE·BE 공동 검토에서 기본 경로·명명·시간·성공 및 오류 응답의 큰 형식·쿠키 인증을 합의했다. 개별 경로와 요청·응답 필드, null 규칙, 쿠키 배포 설정은 상세 명세에서 검토한다.

## DEC-153 — API 문서화 방식과 팀 가이드 (Q-153)

- 가이드·API 계약·요구사항의 로컬 Markdown 링크와 공백 오류를 확인했다. 실행 코드가 아직 없어 실제 문서 화면 호출·인증 검증은 초기 구현 후 진행한다.

## DEC-154 — 호환성이 깨지는 API 변경 순서 (Q-154)

- FE가 사용 중인 필드나 경로를 바꿀 때 BE가 새 규격을 추가하고, FE 전환을 확인한 뒤 기존 규격을 제거하는 순서를 기본으로 할까? 작은 내부 변경은 FE·BE가 같은 적용 시점을 합의하는 안이다.
- 요청자는 동의했다. 새 규격 추가 → FE 전환 확인 → 기존 규격 제거를 기본으로 하며 작은 내부 변경은 FE·BE가 적용 시점을 합의한다.

## DEC-155 — 필수값 검증과 부분 수정 (Q-155)

- 부분 수정 요청에서 필드를 보내지 않으면 기존 값을 유지하고, 비우기 가능한 필드에 null을 보내면 값을 비우는 규칙으로 할까? 필수값에 null을 보내면 검증 오류로 처리하는 안이다.
- 요청자는 필수값을 프론트에서도 검사해야 한다고 했다. FE는 전송 전에 해당 작업에 필요한 필수값을 검사하고 입력 오류를 표시한다. BE는 요청을 다시 검증한다. 부분 수정의 생략·null 규칙은 아직 확정 대기다.
- 요청자는 부분 수정 규칙에도 동의했다. 생략된 필드는 기존 값을 유지하고, null을 허용하는 필드에 null을 보내면 값을 비운다. 필수값에 null을 보내면 검증 오류로 처리한다. FE·BE 모두 작업별 필수값을 검증한다.

## DEC-156 — 목록 기본 정렬과 사용자 정렬 (Q-156)

- 보고서·대화방·변경 이력 목록은 최신 항목을 먼저 보여주고 일정은 시작 시각순으로 보여줄까? 시각이 같으면 내부 ID로 순서를 고정해 페이지 조회의 순서를 안정적으로 유지하는 안이다.
- 요청자는 기본 정렬에 동의한 뒤, 프론트에서 필터를 적용하면 목록 순서도 바꿀 수 있어야 한다고 했다.
- 사용자 정렬을 지원한다. 검토안은 FE가 검색·필터·정렬 조건을 API로 전달하고 BE가 권한·삭제 필터와 검색 조건을 적용한 전체 결과를 정렬한 뒤 페이지를 나누는 것이다.
- 정렬 변경 시 첫 페이지로 이동하고 선택 조건은 이후 페이지에도 유지한다. 허용 정렬 필드·방향은 API별로 정의하고 동률에는 ID 순서를 추가하는 안이다.
- 요청자는 동의했다. 서버에서 권한·삭제 규칙과 검색·필터를 적용한 전체 결과를 정렬한 뒤 페이지를 나눈다. 정렬 변경 시 첫 페이지를 조회하며 이후 페이지에도 같은 조건을 유지한다. 정렬 필드·방향은 API별 허용 목록으로 정의한다.

## DEC-157 — MVP 업무 데이터 보존 기간 (Q-157)

- MVP에서는 공정·검사·보고서·재고 변경 이력을 기간 경과로 자동 영구 삭제하지 않고 보관할까? 운영 전 보존 기간·영구 삭제·백업 정책을 별도로 정하는 안이다. 일반 리소스 삭제에는 기존 soft delete 규칙을 적용한다.
- 요청자는 동의했다. MVP 업무 이력은 자동 영구 삭제 없이 보관하며 운영 전 보존 기간·영구 삭제·백업 정책을 별도로 정한다. 일반 삭제에는 soft delete를 적용한다.

## DEC-158 — 공정·검사 기록의 수정·삭제 (Q-158)

- MVP의 적재된 공정 기록과 시연용 검사 기록은 화면에서 조회만 제공하고, 수정·삭제 관리 화면은 추후 범위로 둘까? 잘못된 초기 데이터는 적재 절차에서 충돌과 변경 이력을 확인한 후 정리하는 안이다.
- 요청자는 수정 기능도 필요하지 않겠냐고 의견을 제시했다.
- 관리자가 공정·검사 기록을 수정·삭제할 수 있게 하고 수정 전후 값·사유·작업자·시각을 기록하며, 삭제에는 soft delete를 적용하는 수정안을 제안했다.
- 요청자는 동의했다. 관리자의 공정·검사 기록 수정·삭제와 변경 이력 보존을 MVP에 포함한다. 고용자는 기존 조회 권한을 유지한다.

## DEC-159 — 공정·검사 기록의 수동 등록 범위 (Q-159)

- 신규 공정 기록은 CSV 적재로 등록하고, 검사 기록은 관리자가 화면에서도 수동 등록할 수 있게 할까? 검사 데이터가 확보되기 전에는 시연 데이터를 준비하고, 화면에서 추가한 검사 기록에도 시연 여부를 표시하는 안이다.
- 요청자는 동의했다. 신규 공정 기록은 CSV 적재로 등록한다. 검사 기록은 관리자 화면에서도 수동 등록할 수 있으며 현재 시연용 검사 기록에는 시연 여부를 표시한다.

## DEC-160 — 공정·검사 수정 후 집계 반영 (Q-160)

- 공정·검사 기록을 수정·삭제하면 이후 공정·검사 조회, 품질 집계와 새 AI 조회·보고서 생성에 반영하고, 이미 생성한 보고서의 저장된 집계 스냅샷은 유지할까? 기존 보고서는 생성 당시 기준이며 최신 수치가 필요하면 새로 생성하는 기존 규칙을 적용하는 안이다.
- 요청자는 동의했다. 이후 조회·품질 집계·새 AI 조회 및 보고서 생성에는 수정·삭제를 반영하고 이미 생성한 보고서의 저장된 집계 스냅샷은 유지한다.

## DEC-161 — 검사 결과 자동 유입 및 수동 등록 제외 (DEC-159 정정)

- 요청자는 검사 결과가 사람이 입력하는 정보가 아니라 자동 검사 시 들어오는 정보이므로 별도 입력창이 필요하지 않다고 정정했다.
- DEC-159의 관리자 검사 기록 수동 등록 합의를 변경한다. 검사 결과는 자동 검사 시스템에서 유입되는 데이터로 취급하고 별도 수동 등록 화면은 만들지 않는다. 실제 검사 데이터·연동이 확보되기 전에는 기존 합의대로 시연 데이터를 준비한다.
- DEC-158의 관리자 수정·삭제 및 변경 이력 보존 합의는 유지한다. 실제 자동 검사 연동 방식은 데이터 원천 확보 후 정한다.

## DEC-162 — 수정·삭제 이력의 조회 권한 (Q-162)

- 공정·검사 기록의 수정·삭제 이력은 관리자가 확인하고, 고용자에게는 수정된 현재 기록만 보여줄까? 관리자는 변경 전후 값·사유·작업자·시각을 확인하는 안이다.
- 요청자는 동의했다. 공정·검사 기록의 수정·삭제 이력은 관리자만 조회한다. 고용자는 기존 권한에 따라 수정된 현재 기록을 조회하며 soft delete된 기록은 일반 조회에서 제외한다. 변경 이력 조회 권한은 서버에서도 검사한다.

## DEC-163 — 가동률 시연 데이터 제공 (Q-163)

- 설비의 실제 가동·정지 시간과 계획 가동 시간이 확보되지 않은 MVP에서는 가동률을 임의로 계산하지 않고 ‘데이터 미확보’로 표시할까? 현재 확인 가능한 사이클 시간과 검사 건수·양품·불량·불량률을 제공하고, 실제 가동률은 필요한 데이터 확보 후 연동하는 안이다.
- 요청자는 가동률도 임의 데이터로 제공하라고 결정했다. MVP에서 가동률 시연 데이터를 준비하고 실제 측정값과 구분되도록 시연 여부를 표시한다. 실제 가동률 데이터 연동은 추후 범위다.

## DEC-164 — 가동률 시연 데이터 구성 (Q-164)

- 가동률 시연 데이터는 설비별·일자별 계획 가동 시간과 실제 가동 시간을 미리 준비하고, ‘실제 가동 시간 ÷ 계획 가동 시간 × 100’으로 계산할까? 기간·설비별 조회에서는 시간을 합산한 뒤 계산하고 계획 가동 시간이 0이면 ‘—’로 표시하며, 화면·AI 답변·보고서에도 시연 데이터임을 표시하는 안이다.
- 요청자는 동의했다. 설비별·일자별 계획 가동 시간과 실제 가동 시간을 시연 데이터로 준비한다. 가동률은 실제 가동 시간 ÷ 계획 가동 시간 × 100으로 계산하며 기간·설비별 조회는 두 시간을 각각 합산한 후 계산한다. 계획 가동 시간 합계가 0이면 ‘—’로 표시한다. 화면·AI 답변·보고서에 시연 데이터임을 표시한다.

## DEC-165 — 검사 판정과 불량 유형의 시연 기준 (Q-165)

- 검사 시연 데이터는 양품·불량 판정을 명시해 준비하고 해당 판정값으로 집계할까? 불량 유형은 시연용 분류를 사용하며 유형이 없는 불량 기록은 ‘미분류’로 집계하고, 실제 자동 검사 판정 기준과 유형 매핑은 데이터 확보 후 정하는 안이다.
- 요청자는 동의했다. 시연 데이터에 양품·불량 판정과 시연용 불량 유형을 미리 넣고 해당 값으로 집계한다. 불량 판정이지만 유형이 없는 기록은 ‘미분류’로 집계한다. 실제 자동 검사 판정 기준과 유형 매핑은 데이터 확보 후 정한다.

## DEC-166 — CSV 재생 종료 시 표시 (Q-166)

- 앞서 보류한 CSV 재생 종료 시에는 마지막 공정 값을 유지하고 ‘시연 종료’와 마지막 데이터 시각을 표시할까? 정상 종료를 ‘갱신 지연’이나 ‘연결 오류’와 구분하고 자동 반복 재생은 하지 않는 안이다.
- 요청자는 동의했다. CSV 재생이 정상 종료되면 마지막 공정 값을 유지하고 ‘시연 종료’와 마지막 데이터 시각을 표시한다. 정상 종료는 갱신 지연·연결 오류와 구분하고 자동 반복 재생은 하지 않는다. Q-008에서 보류한 종료 시 동작을 이 결정으로 확정한다.

## Q-167 — 시연 재시작 방식 (보류)

- 반복 시연이 필요할 때는 개발자가 재생 위치를 처음으로 초기화하는 실행 절차를 제공하고, 별도 재시작 화면은 MVP에서 제외할까? 재시작은 원본 기록을 재적재하거나 보고서·대화·재고 이력을 삭제하지 않고 공정 재생 위치만 초기화하는 안이다.
- 요청자는 시연 관련 논의를 일단 나중으로 넘기자고 했다. 시연 재시작 방식과 실행 절차는 미확정 상태로 보류한다. 앞서 확정한 시연 데이터·계산식·재생 종료 규칙을 취소한 것으로 해석하지 않는다.

## DEC-168 — 일정의 종일·시간 지정 규칙 (Q-168)

- 일정은 종일 일정과 시간 지정 일정을 지원할까? 종일 일정은 한국 기준 날짜로, 시간 지정 일정은 시작·종료 시각으로 입력하고 종료가 시작보다 뒤인지 FE·BE에서 검증하는 기본안이다. 반복·복사는 기존 보류 상태를 유지한다.
- 요청자는 동의했다. 종일 일정과 시간 지정 일정을 지원한다. 종일 일정은 한국 기준 날짜로 처리하고 시간 지정 일정은 한국 시간 기준으로 입력한다. 시간 지정 일정의 종료가 시작보다 뒤인지 FE·BE에서 검증한다. 시간 지정 값의 API 전달·저장은 기존 UTC 계약을 따른다. 반복·복사는 기존 보류 상태를 유지한다.

## DEC-169 — 별도 첨부파일 업로드의 MVP 범위 (Q-169)

- 보고서는 기존 합의대로 DB의 Markdown 본문과 서버 생성 표·그래프를 제공하고, 사용자가 별도 파일을 첨부하는 기능은 MVP에서 제외할까? 보고서 PDF 다운로드는 유지하며 첨부파일 업로드는 실제 요구가 생기면 형식·용량·권한·저장 방식을 정하는 안이다.
- 요청자는 동의했다. 보고서의 별도 첨부파일 업로드는 MVP에서 제외하고 추후 범위로 둔다. Markdown 본문·서버 생성 표·그래프와 PDF 다운로드는 유지한다. 첨부파일 도입 시 형식·용량·권한·저장 방식을 정한다.

## DEC-170 — Markdown 보고서의 표시 범위 (Q-170)

- 보고서 본문은 제목·문단·목록·표·강조·코드 블록 등 기본 Markdown을 지원하고, 본문에 넣은 HTML·스크립트와 임의의 외부 이미지 로딩은 허용하지 않을까? 서버가 생성한 그래프는 별도 관리해 화면과 PDF에 포함하는 안이다.
- 요청자는 동의했으며 S3 같은 외부 스토리지를 고려하지 않았다고 설명했다. 기본 Markdown을 지원하고 본문에 넣은 HTML·스크립트와 임의의 외부 이미지 로딩은 허용하지 않는다. 서버 생성 그래프는 화면과 PDF에 포함한다. 현재 범위에 S3 등 외부 스토리지 도입을 추가하지 않는다. 그래프 제공·재생성 방식은 구현 설계에서 정한다.

## DEC-171 — 서버 생성 그래프의 보관·디자인 기준 (Q-171)

- 그래프는 보고서에 저장한 집계 스냅샷으로 화면 조회·PDF 다운로드 시 서버에서 생성하고, 이미지 파일 자체는 영구 보관하지 않는 방식으로 할까? 외부 스토리지 없이 제공하며 보고서의 수치와 그래프는 같은 저장된 집계 결과를 사용하는 안이다.

- 그래프는 저장된 집계 스냅샷으로 필요할 때 서버에서 생성하고 이미지 파일은 영구 보관하지 않는다. 화면과 PDF에 공통 그래프 스타일을 적용하며 보고서마다 AI가 임의로 디자인을 바꾸지 않는다.

## DEC-172 — 그래프 생성 실패 시 보고서 제공과 사유 안내 (Q-172)

- 그래프 생성만 실패한 경우 보고서 본문과 수치 표는 제공하고 해당 위치에 ‘그래프를 불러오지 못했습니다’를 표시할까? PDF도 본문·표와 그래프 누락 안내를 포함해 제공하고 오류는 서버 로그에 남기는 안이다. PDF 자체 생성 실패는 기존 실패 처리 규칙을 따른다.
- 요청자는 동의했고 실패 이유도 적어 달라고 추가 요청했다.

## DEC-173 — 그래프 재시도 방식 (Q-173)

## DEC-174 — 보고서 생성 실패 시 중간 결과 보관 (Q-174)

## DEC-180 — 실제 작업 중 근무 종료 자동 연장 (Q-180, DEC-112 보완)

- 요청자는 작업 중에는 로그아웃하지 않고 자동 연장하는 편이 편하겠다고 제안했다.

## DEC-181 — 자동 연장의 반복 적용 (Q-181)

- 요청자는 동의했다. 연장된 종료 시각의 10분 전 구간에서도 실제 사용자 작업이 확인되면 다시 1시간 연장한다. 각 종료 예정 시각당 한 번만 적용하고 새 종료 시각을 안내한다. 작업이나 수동 연장이 없으면 종료 시각에 로그아웃한다. 최초 로그인 기준 리프레시 토큰 7일 상한은 유지한다.

## DEC-182 — 다중 탭에서 근무 종료 시각 공유 (Q-182)

## DEC-184 — 주간 보고서의 일요일 시작 (Q-184 일부 확정)

## DEC-197 — 마이그레이션 실행 방식 (Q-197)

- DB 스키마 변경도 서버 시작 시 자동 적용하지 않고 Alembic 명령으로 명시적으로 실행하며, 팀원이 따라 할 적용·현재 버전 확인 절차를 BE/README에 안내할까? 이미 공유·적용한 마이그레이션은 수정하지 않고 후속 파일을 추가하는 기존 저장소 규칙을 따른다. 운영 DB 적용은 별도 명시적 승인을 유지한다.
- 요청자는 Hibernate에 해당하는 개념을 물었다. SQLAlchemy ORM은 Python 객체와 DB 테이블을 연결해 조회·저장을 처리하는 역할이고, Alembic은 테이블·컬럼 등 스키마 변경 이력을 관리·적용하는 역할이라고 설명했다. 공식 참고: https://docs.sqlalchemy.org/en/20/orm/ 및 https://alembic.sqlalchemy.org/en/latest/ . 마이그레이션 명시 실행 제안은 아직 확정 대기다.
- 요청자는 현업 기준을 물었다. 마이그레이션 파일 생성 → 사람이 검토 → 테스트 DB 적용·검증 → 배포의 별도 단계에서 한 번 적용하는 방식을 제안했다. 별도 단계는 로컬 수동 명령 또는 배포 파이프라인 자동 실행일 수 있으며 항상 사람이 수동 실행해야 한다는 뜻은 아니다. Alembic은 자동 생성 결과의 수동 검토를 요구하고 FastAPI는 다중 프로세스에서 마이그레이션 중복 실행을 피하도록 설명한다. 참고: https://alembic.sqlalchemy.org/en/latest/autogenerate.html 및 https://fastapi.tiangolo.com/deployment/concepts/ . 현재 프로젝트에는 로컬 명령·README 안내부터 제공하고 배포 자동화는 환경 확정 후 정하는 안을 제안했으며 확정은 대기한다.
- 요청자는 동의했다. 마이그레이션 파일은 검토·테스트 후 서버 시작과 분리된 단계에서 한 번 적용한다. 로컬에서는 명령으로 적용하고 초기 구성 시 BE/README에 적용·현재 버전 확인 절차를 안내한다. 배포 파이프라인 자동화는 배포 환경 확정 후 정한다. 공유·적용된 파일은 수정하지 않고 후속 파일을 추가하며 운영 DB 적용의 명시적 승인 원칙은 유지한다.

## DEC-198 — 미적용 마이그레이션이 있으면 서버 시작 중단 (Q-198)

- 설명한 사례: 팀원이 최신 코드를 받은 후 DB 변경 적용을 놓치면, 코드에는 새 status 컬럼이 있지만 개인 DB에는 없어 서버 실행 후 보고서 조회 시 오류가 발생할 수 있다. 시작 단계에서 확인하면 ‘DB 업데이트 필요’로 원인을 즉시 안내할 수 있다.
- 선택의 성격: 미적용 변경이 있다는 이유로 서버 시작을 반드시 막아야 하는 보편적 의무는 아니다. 현재 팀의 초기 개발 단계에서는 코드·개인 DB 버전 불일치를 빨리 발견하도록 시작을 중단하는 정책을 제안했다.
- 요청자는 적용에 동의했으며 ‘나중에 확인할 수 있게 확실하게 히스토리를 남겨 달라’고 명시했다.
- 확정 동작: 서버 시작 시 현재 DB의 마이그레이션 버전과 코드의 적용 대상 버전을 확인한다. 미적용 마이그레이션이 있으면 서버 시작을 중단하고 ‘마이그레이션 적용 필요’와 해당 환경에서 실행할 적용 절차를 안내한다. 자동으로 DB 스키마를 변경하지 않는다. 개발자가 적용한 뒤 서버를 다시 실행한다.
- 근거·후속 확인: DEC-197의 명시적 별도 적용 원칙을 유지하면서 팀원의 적용 누락을 조기에 발견하기 위한 결정이다. 초기 구성 시 BE/README에 증상·원인·적용 명령·현재 버전 확인·재실행 순서를 문서화하고, 미적용 상태의 시작 실패와 적용 후 정상 시작을 검증한다. 현재는 정책 확정이며 시작 검사 코드를 구현·검증한 상태는 아니다. 버전 일치만으로 모든 수동 스키마 변경까지 검증된다고 간주하지 않는다.

- 기술 판단으로 계정·조직·설비·품목 마스터와 CSV 적재·공정 기록·재생 상태를 두 개의 후속 마이그레이션으로 분리했다. 라인과 품목 코드는 원천에 없을 수 있어 nullable로 두고, 사이클은 `cycle_time_seconds`로 단위를 명시한다. 원본 파일 fingerprint와 파일 내 행 번호 조합으로 중복 행을 식별하고 원문은 JSONB로 보존한다.
- 설비 상태·가동률·생산 목표·생산 수량은 근거 데이터가 생기기 전까지 추론하지 않는다. CSV TimeStamp 원본 시간대와 실제 운영 라인 데이터는 기존 보류를 유지한다.

## TECH-006 — 공정 CSV 원자적 적재와 원천 키

- MR !19 병합 후 요청자는 다음 작업을 이어가도록 했다. 구현 우선순위에 따라 실제 CSV 적재 기반과 설비·제품 마스터 연결을 후속 범위로 선택했다.
- elice_v1.csv, labeled_data.csv, unlabeled_data.csv를 다시 확인한 결과 모두 `_id`를 제공하며 elice_v1과 labeled 데이터에는 동일 `_id`가 재등장한다. `_id`는 source namespace 안의 원천 레코드 키로 사용하고 `(source_namespace, source_record_key)` UNIQUE를 추가한다.
- 동일 파일 fingerprint 재적재는 거부한다. 다른 파일에서 같은 원천 키와 같은 전체 payload가 재등장하면 건너뛰고, payload가 다르면 조용히 덮어쓰지 않고 전체 적재를 롤백한다. 파일 내 중복에도 같은 규칙을 적용한다.
- CSV 필수 헤더·TimeStamp 형식·Cycle_Time의 유한 비음수 값을 검증한다. Cycle_Time의 0은 실제 데이터에 있으므로 누락으로 바꾸지 않고 0초로 보존한다.
- EQUIP_CD와 EQUIP_NAME으로 설비를 연결하고 PART_NO가 있으면 제품 코드로 연결한다. 코드가 없는 파일은 제품명으로 미코드 제품을 연결하며 이후 같은 이름의 PART_NO가 확인되면 해당 제품에 코드를 보강한다. 같은 업무 코드에 다른 이름이 들어오면 마스터 충돌로 중단한다.
- CSV 전체 적재, 마스터 생성, 초기 replay 생성은 한 트랜잭션으로 처리한다. Repository는 flush까지만 수행하고 Service가 트랜잭션 경계를 소유한다. 대용량 파일은 1,000행 기본 배치로 처리하되 최종 commit은 전체 성공 후 한 번만 수행한다.
- 원본 TimeStamp의 실제 시간대는 계속 보류한다. 잘못된 기본값으로 데이터를 확정하지 않도록 CLI의 `--source-timezone`을 필수로 두고 IANA 시간대를 명시하게 한다.

## DEC-202 — 공정 CSV 원본 시간대

- 공정 CSV의 오프셋 없는 `TimeStamp`를 한국시간(`Asia/Seoul`)으로 해석할지 요청자에게 확인했다.
- 요청자는 동의했다. 적재 시 한국시간을 기본 원본 시간대로 적용하고 PostgreSQL에는 UTC 기준 `timestamptz`로 저장한다. 다른 시간대의 새로운 원천은 적재 명령에서 IANA 시간대를 명시해 기본값을 덮어쓴다.

## TECH-008 — 인증 비밀번호 해시·JWT 라이브러리 선정

- DEC-063과 REQUIREMENTS가 초기 구현으로 미뤄 둔 비밀번호 해시·JWT 라이브러리를 선정했다.
- 비밀번호는 Argon2id(`argon2-cffi`)를 사용한다. 라이브러리 자체 검증 API로 저장 해시와 입력값을 비교하고, 해시 생성은 초기 계정 적재·비밀번호 변경·초기화에서 같은 함수(`app/security/passwords.py`)를 쓴다.
- 토큰은 HS256 JWT(`PyJWT`)를 사용하고 `APP_JWT_SECRET`(32자 이상)으로 서명한다. 리프레시 토큰도 JWT로 발급하되 원문은 저장하지 않고 SHA-256 digest만 DB에 남긴다. 재사용 감지와 세대 교체는 후속 갱신 API에서 구현한다.
- Python 3.14 기준 `argon2-cffi` 25.1.0, `PyJWT` 2.15.1을 고정 설치했고, Windows 로컬 3.12 환경에서도 동작을 확인했다.

## TECH-009 — 초기 계정 준비 방식과 FE 연동 출처·CSRF 방식

- FE 연동을 앞두고 초기 계정 준비 방식, CORS 허용 출처, CSRF 방식을 요청자와 확정했다.
- 초기 계정은 Alembic 데이터 마이그레이션이 아니라 CLI(`python -m app.commands.seed_accounts`)로 만든다. 비밀번호는 인자로 넘기거나 화면에 남지 않게 입력받아 저장소에 남기지 않는다. 같은 사번이 있으면 덮어쓰지 않고 실패시켜 비밀번호가 조용히 교체되는 일을 막는다. 초기 계정은 `must_change_password=true`로 만들어 최초 로그인 후 변경을 요구한다.
- FE 개발 출처는 `http://localhost:5173`, `http://localhost:5174`를 `APP_CORS_ORIGINS` 설정으로 허용한다. 자격 증명을 허용해야 하므로 와일드카드 출처를 사용하지 않고 명시한 출처만 허용한다. 목록이 비어 있으면 CORS 미들웨어를 추가하지 않는다.
- CSRF는 더블 서브밋 쿠키 방식으로 구현한다. 로그인 시 JS가 읽는 `imleader_csrf_token` 쿠키를 발급하고, 쿠키 인증 상태 변경 요청은 `X-CSRF-Token` 헤더로 같은 값을 보낸다. 실제 검증은 리프레시·로그아웃 API를 구현하는 다음 MR부터 적용한다.
- CSRF 방식을 확정하기 전까지는 로그인·현재 사용자 조회만 제공하므로 상태 변경 쿠키 요청 자체가 없다. FE 연동 문서는 `API_SPEC.md`의 인증 연동 계약에 둔다.

## TECH-010 — 리프레시 회전·재사용 감지와 동시 갱신 처리

- DEC-107은 폐기된 리프레시 재사용 시 세션을 폐기하되 "실제 동시 갱신 요청을 중복 전송과 구별하는 기준은 구현 설계에서 정한다"고 남겨 두었다. 그 기준을 정했다.
- 리프레시 자격 증명 행을 `SELECT ... FOR UPDATE`로 잠그고 세대를 1 증가시켜 회전한다. 이전 행은 삭제하지 않고 `consumed_at`을 기록해 재사용을 감지한다(토큰 원문은 저장하지 않음).
- 직전 세대가 `APP_REFRESH_REUSE_GRACE_SECONDS`(기본 10초) 안에 다시 제출되면 같은 세션의 중복 요청으로 보고 `409 REFRESH_IN_PROGRESS`만 반환하며 세션을 폐기하지 않는다. FE는 이 경우 재시도한다.
- 유예를 지났거나 그보다 오래된 세대가 제출되면 재사용으로 판단해 세션과 현재 리프레시를 폐기하고 `401 SESSION_REVOKED`를 반환한다. 다른 기기 세션은 유지한다.
- 새 리프레시 만료는 항상 세션의 `absolute_expires_at`으로 제한해 최초 로그인부터 7일 상한을 유지한다(DEC-052·053). 유예 시간은 설정값이며 0으로 두면 유예 없이 즉시 재사용으로 판정한다.
- 로그아웃은 해당 세션과 현재 리프레시만 폐기한다. 이미 발급된 액세스 토큰은 만료까지 유효하다는 DEC-054를 그대로 유지하므로 `/auth/me`는 세션 폐기를 검사하지 않는다.


## TECH-010 — 공정 CSV 5초 재생 구현

- DEC-006·DEC-166·DEC-202에 따라 적재된 CSV 레코드를 첫 실행 시 즉시, 이후 5초마다 하나씩 공개하는 재생 Service와 CLI worker를 구현했다.
- `ProcessReplayService`가 트랜잭션을 소유하고 Repository의 `SELECT ... FOR UPDATE`로 replay 행을 잠근다. 같은 replay를 여러 worker가 실행해도 cursor와 공개 시각을 한 worker만 변경한다.
- 마지막 레코드를 공개한 트랜잭션에서 상태를 `completed`로 바꾸며 마지막 `data_time`과 공개 값을 유지한다. 빈 replay도 `completed`로 종료하고 자동 반복하지 않는다.
- 조회용 상태 계산은 실행 상태가 `running`이고 마지막 정상 갱신 후 15초 이상 지났을 때만 `delayed`를 반환한다. 정상 종료 `completed`와 명시적 실패 `failed`는 지연 상태로 덮어쓰지 않는다.
- 별도 스키마·API 계약 변경은 없다. 현재 공정 조회 API와 FE polling 연동은 후속 작업으로 남긴다.
- Ruff, mypy, 전체 pytest와 PostgreSQL 18에서 두 레코드 replay가 5초 간격으로 진행되어 마지막에 종료되는 동작을 검증했다.
- 기록일: 2026-11-20.

## TECH-011 — 현재 공정 조회 API 계약

- 후속 우선순위에 따라 인증된 관리자·고용자가 사용하는 `GET /api/v1/process/current`를 구현했다. 별도 역할 제한 없이 기존 DEC-152 조회 권한을 적용한다.
- 현재 시연은 ID가 가장 큰 최신 replay를 기준으로 한다. 해당 import에서 조회 시각까지 공개된 레코드만 대상으로 설비별 source 행 순서가 가장 뒤인 1건을 반환하며, 선택 `equipment_id` 필터를 지원한다.
- 응답에 서버 `queried_at`, replay의 `data_time`·`last_advanced_at`·상태, 설비·품목·최근 사이클 시간·공개 시각·시연 여부를 명시한다. replay가 없거나 공개 전이면 polling 가능한 200 빈 목록을 반환한다.
- CSV에 없는 설비 상태·생산량·진행률을 추론하지 않는다. DEC-007에 따라 설비 상태는 `unknown`으로 제공하고, 작업 진행률은 DEC-006에 따라 응답에서 제외했다.
- `cycle_time_seconds`는 PostgreSQL numeric 정밀도를 잃지 않도록 JSON 문자열로 전송한다. 날짜·시각은 공통 계약대로 UTC RFC 3339를 사용한다.
- DB 스키마와 마이그레이션 변경은 없다. FE polling과 화면의 시연·기준·조회·오류 상태 표시는 후속 확인으로 남긴다.
- 기록일: 2026-11-20.
