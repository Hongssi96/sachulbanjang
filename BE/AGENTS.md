# Backend 추가 작업 지침

이 문서는 루트 `AGENTS.md`의 공통 규칙을 대체하지 않는다. `BE/`에서 작업할 때 공통 규칙에
아래 지침을 추가로 적용한다. 요구사항과 구현 상태를 이 문서에 복제하지 않고 관련 원본 문서를
확인한다.

## 1. 작업 범위

- 기본 수정 범위는 `BE/`다.
- FE 파일과 루트 공통 파일은 이해를 위해 읽을 수 있지만 명시적으로 승인받기 전에는 수정하지
  않는다.
- 작업 시작 전에 현재 브랜치, 미커밋 변경, 진행 중인 Git 작업과 최신 개발 브랜치 기준 여부를
  확인한다.
- 관련 GitLab Issue, 선행 MR과 MR의 인수인계를 확인한다. 접근할 수 없는 정보는 확인했다고
  표현하지 않는다.
- 다른 작업자의 변경을 덮어쓰거나 관련 없는 리팩터링·포맷 변경을 섞지 않는다.

## 2. 관련 문서 확인

작업과 직접 관련된 문서만 선택해 읽되, 다음 문서를 기준 원본으로 사용한다.

- 업무 요구사항·완료 조건: `BE/docs/REQUIREMENTS.md`
- 기존 결정·질문·보류: `BE/docs/DECISION_HISTORY.md`
- API 계약·구현 상태: `BE/docs/API_SPEC.md`
- DB 제약·관계: `BE/docs/DATABASE_DESIGN.md`, `BE/docs/ERD.md`
- 구조·책임 분리: `BE/docs/ARCHITECTURE.md`, `BE/docs/DOMAIN_MODEL.md`
- 검증 범위: `BE/docs/TEST_PLAN.md`
- 실행·마이그레이션 명령: `BE/README.md`

기존 결정이나 보류 사항을 반복해서 질문하지 않는다. 문서와 코드로 판단할 수 없는 실제 업무
규칙·권한·데이터 의미만 사용자에게 확인한다.

## 3. 구현과 기록

- Router는 요청·응답, Service는 업무 규칙과 트랜잭션, Repository는 데이터 접근 책임을 갖는다.
- Repository는 임의로 commit하지 않는다. 함께 성공해야 하는 변경은 Service가 하나의
  트랜잭션으로 처리한다.
- 스키마 변경은 새 Alembic migration으로 추가하며 이미 공유·적용된 migration을 수정하지 않는다.
- 실제 구현된 DB 구조가 바뀌면 `BE/docs/ERD.md`의 Mermaid와 DB 설계를 함께 갱신한다.
- API 작업은 `BE/docs/API_SPEC.md`에 세부 완료·미완료와 검증 근거를 갱신한다.
- 중요한 사용자 질문·답변과 되돌리기 어려운 기술 판단은 `BE/docs/DECISION_HISTORY.md`에 남긴다.
- 구현 일부가 끝났다는 이유로 상위 기능 전체를 완료로 표시하지 않는다.

## 4. 검증과 커밋

- `BE/README.md`, `BE/pyproject.toml`, CI에 존재하는 명령만 실행한다.
- 변경 범위에 맞춰 Ruff, mypy, pytest와 필요한 PostgreSQL·Alembic 검증을 수행한다.
- 실행하지 못한 검증은 항목과 이유를 남긴다.
- 논리적으로 연결된 변경 단위로 커밋하고 루트 `AGENTS.md`의 Git convention을 따른다.
- commit, push, MR 생성·수정, merge는 사용자 승인 범위에서만 수행한다.

## 5. MR 인수인계

BE MR 설명에는 기존 MR 템플릿 항목과 함께 다음 인수인계를 포함한다.

```md
## ⏭️ 인수인계

### 완료한 항목
-

### 미완료 항목
-

### 다음 권장 작업
-

### 주의할 제약·가정
-

### 보류된 결정
-

### 실행하지 못한 검증
- 항목:
- 이유:
```

- 완료 항목은 실제 구현과 해당 검증이 끝난 범위만 적는다.
- 검증 명령과 결과, 변경된 API·DB·환경변수, 관련 Issue·선행 MR을 함께 기록한다.
- 다음 작업자는 최신 개발 브랜치와 선행 MR의 인수인계를 확인한 뒤 미완료 범위에서 이어간다.
- 작업 브랜치에만 존재하는 문서 상태를 개발 브랜치에 병합된 현재 상태로 간주하지 않는다.
